# 上下文管理对比：压缩与交接

## Coder 上下文管理

### 实现位置
`src/features/agent/context-monitor.ts` + `src/features/agent/handoff.ts`

### 策略：Handoff（会话交接）

当上下文接近 token 上限时，Coder 不压缩当前对话，而是：

1. **检测触发**：`shouldTriggerContextHandoff()` 检查已用 token 是否超过阈值
2. **生成交接文档**：AI 按结构化模板编写交接内容
3. **创建新会话**：将交接文档注入新会话继续执行

```typescript
// 触发条件
usedTokens >= thresholdTokens (默认 80%) AND remainingTokens <= reservedTokens

// 交接文档结构
## Original User Intent
## Current Objective
## Constraints
## Completed
## In Progress
## Pending Next Actions
## Key Decisions
## Rejected Or Superseded Approaches
## Artifacts And Evidence
## Background Jobs And Follow-ups
## Open Questions
## Resume Instructions
```

### Token 估算
- 使用 `tokenlens` 库估算文本 token 数
- 图片固定估算 765 tokens
- 考虑 content、reasoning_content、tool_calls 全部字段

### 参数配置
| 参数 | 默认值 | 说明 |
|------|--------|------|
| triggerThreshold | 0.80 | 触发交接的阈值比例 |
| handoffReserveRatio | 0.25 | 预留 token 比例（用于生成交接文档） |
| minReserveTokens | 1,000 | 最小预留 tokens |
| maxReserveTokens | 24,000 | 最大预留 tokens |

## Claude Code 上下文管理

### 策略：三层压缩系统

#### 第一层：MicroCompact（局部清除）
- **触发**：工具输出过长时自动触发
- **方式**：将旧工具输出替换为 `[Old tool result content cleared]`
- **白名单**：Read、Bash、Grep、Glob、WebSearch、WebFetch、Edit、Write
- **时间衰减**：越旧的工具输出越容易被清除
- **无需 API 调用**

#### 第二层：Session Memory Compact（摘要替换）
- **触发**：自动压缩阈值到达时
- **方式**：用已提取的 Session Memory 替换压缩部分
- **保留窗口**：至少 10K tokens、至少 5 条文本消息、最多 40K tokens
- **工具对保护**：确保 tool_use 和 tool_result 成对保留
- **无需 API 调用**

#### 第三层：传统 API 摘要（最后手段）
- **触发**：手动 `/compact` 或前两层不可用时
- **方式**：调用 AI 模型生成对话摘要
- **预处理**：stripImages → stripReinjectedAttachments
- **后处理**：重新注入关键上下文（50K token 预算）
  - 恢复最近 5 个文件内容（每文件 5K tokens）
  - 恢复已激活技能指令（总计 25K tokens）
  - 重新注入 CLAUDE.md

### CompactBoundary 机制
每次压缩后插入 `SystemCompactBoundaryMessage`，后续操作只处理 boundary 之后的消息。包含：
- `compactType`: auto / manual / micro
- `preCompactTokenCount`: 压缩前 token 数
- `preservedSegment`: 保留的消息 UUID

### PTL 紧急降级
当压缩后仍超出限制（Prompt Too Long, 413 错误）：
1. **Context Collapse Drain**：提交已暂存的折叠
2. **Reactive Compact**：更激进的即时压缩
3. **Truncate Head**：直接截断最早消息

## 对比分析

| 维度 | Coder | Claude Code |
|------|-------|-------------|
| **核心策略** | Handoff（创建新会话） | 三层压缩（在当前会话内压缩） |
| **压缩层级** | 0 层（无局部压缩） | 3 层（MicroCompact → SM → API 摘要） |
| **API 调用** | 交接时需要 AI 生成文档 | MicroCompact/SM 无需 API，只有第三层需要 |
| **上下文连续性** | 新会话丢失原始消息链 | 压缩后保留边界标记，维持连续性 |
| **工具对保护** | 无（新会话从头开始） | 确保 tool_use/tool_result 成对保留 |
| **恢复机制** | Fallback Handoff Body（固定模板） | 50K token 重新注入预算 |
| **紧急降级** | 无 | Context Collapse → Reactive Compact → Truncate |
| **压缩边界标记** | 无 | CompactBoundary Message |

## Coder 可学习的思想

### 1. 引入 MicroCompact
在 Handoff 之前，先尝试清除旧工具输出（glob、grep、shell 结果等），可以显著延长当前会话寿命，减少交接频率。

**优势**：
- 无需 API 调用，零成本
- 保留对话的连续性，AI 不需要重新理解上下文
- 交接文档本身也需要 token 空间，减少交接次数等于节省 token

### 2. CompactBoundary 边界标记
每次压缩后插入边界消息，后续操作只处理边界后的消息。这使得：
- 压缩范围精确可控
- 避免重复压缩已处理的消息
- 支持会话恢复时正确重建状态

**建议**：Coder 可在消息模型中引入 `compactBoundary` 类型，跟踪最后一次压缩的位置。

### 3. 工具对完整性保护
Claude Code 的 `adjustIndexToPreserveAPIInvariants()` 确保压缩不会切断 tool_use/tool_result 对。这是 API 正确性的关键保证。

**建议**：Coder 在实现任何压缩机制时，必须保证消息对的完整性。

### 4. 重新注入预算
Claude Code 压缩后通过 50K token 预算重新注入关键上下文（文件内容、技能指令、CLAUDE.md）。Coder 的 Handoff 依赖 AI 自行总结，可能遗漏关键信息。

**建议**：Coder 的交接过程可引入结构化恢复机制，确保关键上下文（如 AGENTS.md、最近编辑的文件）在新会话中自动恢复。

### 5. PTL 紧急降级策略
当压缩后仍然超出限制时的三级降级（Collapse Drain → Reactive Compact → Truncate Head）是成熟的容错链。

**建议**：Coder 可在 Handoff 失败时提供降级方案，如直接截断最早消息而非完全放弃。

### 6. Session Memory 概念
Claude Code 的 Session Memory 在对话过程中持续提取关键信息，压缩时直接用已有摘要替换，无需额外 API 调用。

**建议**：Coder 可在 Agent Loop 运行期间维护一个轻量级摘要（如关键决策、文件修改记录），Handoff 时直接使用而非让 AI 重新总结。

### 7. 交接 vs 压缩的权衡
Coder 选择 Handoff（创建新会话）而非压缩，优势是干净的状态重置，劣势是上下文断裂。Claude Code 选择压缩，优势是连续性，劣势是实现复杂度高。

**建议**：Coder 可考虑混合策略——优先 MicroCompact 延长当前会话寿命，实在无法压缩时才 Handoff。这样兼顾连续性和正确性。
