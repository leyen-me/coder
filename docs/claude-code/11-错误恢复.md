# 错误恢复与容错对比：健壮性设计

## Coder 错误恢复机制

### Chat Retry（聊天重试）
```typescript
// chat-retry.ts

// 两种可恢复错误：

//    → 仅在没有已流式输出时重试
```

```typescript
  // 检测 AI 是否重复调用相同工具（相同参数）

```

### Proxy Decision（代理决策）
长任务会话中，AI 给出最终答案后：
1. 构建决策请求（包含 AI 回答、会话策略）
2. 调用独立模型判断是否继续
3. 若继续 → 注入 continuation prompt → 进入下一轮
4. 若完成 → 结束会话

### Handoff（上下文交接）
当 token 用量超过阈值：
1. AI 生成交接文档（结构化模板）
2. 创建新会话，注入交接内容
3. 在新会话中继续执行

## Claude Code 错误恢复机制

### 7 种终止条件
| 原因 | 触发位置 | 机制 |
|------|---------|------|
| completed | AI 未发出 tool_use | 正常完成 |
| blocking_limit | Token 超硬限制 | 生成 PTL 错误消息 |
| aborted_streaming | abortController.signal.aborted | 为未完成工具生成合成结果 |
| model_error | callModel() 抛异常 | 生成错误消息 |
| prompt_too_long | 413 错误且 reactive compact 无法恢复 | 释放暂扣错误 |
| image_error | 图片尺寸/大小错误 | 直接返回 |
| stop_hook_prevented | Stop hook 返回 preventContinuation | Hook 阻止继续 |

### 4 种恢复路径

#### 1. max_output_tokens 恢复
```
首次: maxOutputTokens 从默认值提升到 ESCALATED_MAX_TOKENS (64K) → 静默重试
后续: 注入恢复消息 "Output token limit hit. Resume directly..."
     → 最多重试 MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3 次
```

#### 2. Prompt-Too-Long 恢复
```
阶段1: Context Collapse Drain — 提交已暂存的折叠，释放空间后重试
阶段2: Reactive Compact — 触发即时压缩，生成摘要后重试
阶段3: truncateHeadForPTLRetry() — 直接截断最早消息
```

#### 3. Stop Hook 阻塞重试
Stop hook 注入阻塞错误消息 → AI 重新思考 → 下一轮迭代

#### 4. 模型降级（Fallback）
```
主模型不可用 (FallbackTriggeredError)
  → 清空已收集的 assistantMessages
  → tool_use 块收到合成结果 "Model fallback triggered"
  → 移除思维签名块（跨模型回放会 400）
  → 切换到 fallbackModel
  → 生成系统消息 "Switched to {fallback} due to high demand..."
  → 重新发起流式请求
```

### Denial Tracking（拒绝追踪）
```typescript
const DENIAL_LIMITS = {
  maxDenialsPerTool: 3,        // 同一工具连续拒绝上限
  cooldownPeriodMs: 30_000,    // 冷却期 30 秒
}
// 连续拒绝 → 注入消息 "Your previous tool call was rejected..."
// 强制 AI 改变策略
```

### Token Budget（实验性）
```
continuation: 未达预算但超阈值 → 注入 nudge 消息加速收尾
diminishing_returns: 检测收益递减 → 提前终止
```

## 对比分析

| 维度 | Coder | Claude Code |
|------|-------|-------------|
| **重试次数** | 最多 3 次 | 按错误类型不同（output_tokens: 3次, PTL: 2阶段） |
| **流空闲恢复** | ✅ buildStreamIdleRecoveryMessages | ❌ 无专门处理 |
| **输出截断恢复** | ❌ | ✅ max_output_tokens → 提升上限重试 |
| **PTL 恢复** | ❌（依赖 Handoff） | ✅ 三级降级（Collapse → Reactive Compact → Truncate） |
| **模型降级** | ❌ | ✅ 自动切换到 fallback 模型 |
| **停滞检测** | ToolCallStallDetector（重复调用） | Denial Tracking（连续拒绝） |
| **Hook 阻塞恢复** | ❌ | ✅ Stop Hook 注入错误消息强制重思考 |
| **Token Budget** | Proxy Decision（独立模型判断） | Token Budget Tracker（收益递减检测） |

## Coder 可学习的思想

### 1. 按错误类型的差异化恢复
Claude Code 针对不同错误类型有不同的恢复策略：
- max_output_tokens → 提升上限重试
- prompt_too_long → 压缩后重试
- model_error → 模型降级

**建议**：Coder 的 Chat Retry 可扩展为按错误类型分类的恢复策略，而非通用重试。例如：
- 429 Rate Limit → 延长等待后重试
- 413 Prompt Too Long → 触发 MicroCompact 或提前 Handoff
- Connection Error → 指数退避重试

### 2. 模型降级机制
当主模型不可用时自动切换到备用模型，确保任务不中断。这是一个重要的生产级容错特性。

**建议**：Coder 可配置 primary/fallback 模型对，主模型连续失败时自动降级。

### 3. max_output_tokens 恢复
AI 输出被截断时，首次静默提升 maxOutputTokens 到 64K 重试（用户无感知），后续注入恢复消息让 AI 继续。

**建议**：Coder 在检测到输出截断时可尝试提升 max_tokens 参数后重试。

### 4. Denial Tracking 替代 Stall Detection
Claude Code 的 Denial Tracking 检测"连续被拒绝"而非"重复调用"，更精准地识别 AI 的死循环行为。

**建议**：Coder 可补充拒绝追踪机制——当 ask_question 被用户连续拒绝时，注入消息引导 AI 换策略。

### 5. Stop Hook 阻塞恢复
Stop hook 可以注入错误消息让 AI 重新思考，而非直接终止。这给了 AI 自我纠正的机会。

**建议**：Coder 在引入 Hook 系统后，可支持 Hook 的阻塞重试能力——Hook 返回 block 时注入错误消息到对话，让 AI 修正后继续。

### 6. 合成 Tool Result
当流中断时，Claude Code 为未完成的 tool_use 生成合成 tool_result（如 "Model fallback triggered"），确保消息对完整性。

**建议**：Coder 在 Agent 取消或异常终止时，为未完成的工具调用生成合成结果，保持消息链完整。

### 7. Token Budget 收益递减检测
Claude Code 的 Token Budget Tracker 跨迭代累计 token 消耗，检测到收益递减时提前终止，防止 AI 无效循环。

**建议**：Coder 可引入类似的预算追踪——当连续多轮工具调用未产生有意义的进展时，主动触发 Proxy Decision 或终止。
